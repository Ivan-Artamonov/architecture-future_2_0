# Обоснование изменений

## 1. Доменные продукты данных и контрактные интеграции

Бизнес-логика переносится из общего DWH в доменные системы. Головной офис, клиники, финтех, ИИ-сервисы и будущие партнеры владеют своими продуктами данных и публикуют их через API и события. Новые интеграции строятся через Apache Kafka. Это сокращает число согласований и позволяет доменам выпускать изменения независимо. Новый финтех-сервис или партнер подключается без изменения бизнес-логики общего DWH. Появляются расходы на Kafka, мониторинг, хранение событий и поддержку совместимости схем.

## 2. Облачная платформа, IaC и надежность

Инфраструктура описывается Terraform и разворачивается в отдельных средах доменов. Kubernetes запускает контейнерные сервисы, а мониторинг, логи, секреты, backup становятся общими платформенными возможностями. Облако позволяет масштабировать сервисы и пайплайны при росте объема данных и числа бизнесов. IaC уменьшает ручные ошибки и ускоряет создание сред

## 3. Lakehouse, пайплайны и data governance

Вместо постоянного расширения единого DWH создаются raw и curated-слои в Lakehouse. Пайплайн загрузки принимает данные и выполняет преобразования. Каталог данных и семантика хранят бизнес-глоссарий, владельцев, lineage и качество. Это отделяет аналитическую нагрузку от операционного DWH, сокращает время подготовки отчетов и сохраняет исходные данные для повторной обработки. Единый каталог повышает доверие к показателям и упрощает поиск причин ошибок. Риски - усложнение пайплайнов и необходимость постоянного участия владельцев данных.

## 4. Портал самообслуживания и управление доступом

Портал обращается к подготовленным продуктам через API gateway с использованием бизнес-моделей. IAM применяет RBAC/ABAC, маскирование и аудит. Пользователь получает отчет или создает собственный отчет без ручной сборки запроса командой DWH. Изменение ускоряет принятие управленческих решений и уменьшает очередь запросов к аналитикам

## 5. Изолированный медицинский контур для ИИ

Медицинские данные передаются ИИ-сервисам только через защищенный медицинский API. В аналитический lakehouse направляются лишь разрешенные агрегатные данные и технические метаданные. Так ИИ сохраняет возможность работать с медицинскими данными, а аналитическая витрина не становится источником доступа к ним.

## 6. Постепенный вывод легаси

SQL Server 2008, PowerBuilder и Apache Camel временно сохраняются в отдельных доменах и подключаются через адаптеры. Новая функциональность реализуется в доменных сервисах, а легаси выводится по мере готовности миграции. Поэтапный подход снижает риск простоя.
