# Обоснование Terraform-конфигурации

Конфигурация реализует минимальный IaaS-foundation для целевой архитектуры данных «Будущего 2.0». Она не разворачивает целиком Kafka, lakehouse и портал самообслуживания. Эти сервисы являются следующим прикладным слоем и могут быть размещены на созданной VM или подключены позднее как отдельные облачные сервисы.

## Управляемые ресурсы

Terraform управляет:
- виртуальной машиной `future-2-0-app`;
- загрузочным диском `network-ssd` объемом 10 ГБ;
- сетевым интерфейсом VM;
- подключением к существующей subnet;
- NAT для исходящих соединений;
- SSH-ключом, переданным через metadata;
- параметрами зоны и вычислительных ресурсов.

## Размеры ресурсов

VM использует 2 vCPU и 2 ГБ RAM. Этого достаточно для тестового сервиса, проверки SSH и демонстрации жизненного цикла Terraform. Для production-портала и data pipeline размер нужно подбирать по нагрузочному тестированию или профилю предполагаемой нагрузки.

Загрузочный диск имеет размер 10 ГБ и тип `network-ssd`. Размер выбран с учетом стандартной квоты на SSD-диски в одной зоне доступности. 

## NAT

Параметр `nat = true` выдает VM публичный NAT-адрес для исходящего доступа. Это позволяет установить обновления, скачать пакеты и получить образы контейнеров. В проде лучше использовать private subnet без публичного IP и отдельный NAT Gateway.

## Почему Terraform

Terraform использует декларативный язык HCL: в конфигурации описывается желаемое состояние, а не последовательность ручных действий. Провайдер Yandex Cloud сопоставляет это состояние с реальными ресурсами.

Преимущества:

- IaC
- предварительная проверка изменений через `terraform plan`
- отслеживание состояния ресурсов в `terraform.tfstate`
- повторяемость и быстрый откат конфигурации
- масштабирование параметров через variables
- уменьшение количества ручных ошибок
